ISO Timestamp Versioning

Versions are based on release time and always use the shortest ISO 8601 date fragment needed for the project at that point.

Prefix versions with v, for example v1991-08-06.

Core Rule

Start with release date in UTC and pick the shortest ISO timestamp that uniquely identifies the release among all releases of the same app.

  • YYYY when there is only one release in that year.
  • YYYY-MM when there are multiple releases in the same year.
  • YYYY-MM-DD when there are multiple releases in the same month.
  • YYYY-MM-DDThh if needed for multiple releases in one day.
  • YYYY-MM-DDThh:mm or YYYY-MM-DDThh:mm:ss only if collisions continue.

Example Timeline

Release Date (UTC) Version Why
1989-03-12 (initial submission) v1989 First milestone in 1989, so year precision is enough.
1990-11-12 (proposal approved path) v1990 Only milestone in 1990, so year precision is enough.
1991-03-15 (early implementation milestone) v1991-03 Now there are multiple 1991 milestones, so month precision is needed.
1991-07-15T09 (internal demo build) v1991-07 First July milestone, so month precision is still enough.
1991-07-15T14 (same-day follow-up build) v1991-07-15T14 Second release on the same day, so hour precision is required.
1991-08-01 (pre-public handoff) v1991-08 First August milestone, so month precision is enough.
1991-08-06 (released to the public) v1991-08-06 Second August milestone, so day precision is required.

How To Use It

  1. Store a canonical release timestamp in UTC for each shipped build.
  2. Generate the shortest unique ISO fragment for that release.
  3. Add the v prefix and publish as your version label.
  4. Use the same label in changelogs, release notes, and build metadata.

This gives immediate chronological ordering and avoids debates over whether a change is major, minor, or patch.

Practical Notes

  • Use UTC to avoid timezone drift.
  • Do not skip leading zeros, keep ISO formatting strict.
  • If releases are generated automatically, include hour/minute only when required.
  • For API compatibility signaling, pair this with a separate compatibility policy document.
